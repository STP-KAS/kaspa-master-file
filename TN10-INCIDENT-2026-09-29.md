# TN10 incident, 29 Sep 2026: private fork from mining on an unsynced node

stp's own Testnet-10 (TN10) stack on the desk box. Testnet only. No mainnet impact, no real rewards, nothing posted publicly. Times are Europe/Brussels (CEST, UTC+2). Written from the TN10 watch and TN10 ops reports that evening.

## What happened

| Time (CEST) | Event |
| --- | --- |
| 20:13 | The box rebooted. The reboot wiped `/tmp`, and n0's kaspad data dir lived there, so the node's database was gone. |
| after 20:13 | TN10 ops rebuilt n0 with its data dir under `/workspace`. It still ran with `--enable-unsynced-mining`. |
| ~20:34 | The 6 pool miners (about 31 MH/s combined) started while n0 was still in IBD (initial block download): DAA score around 82k, about 31% of headers. |
| 20:34–22:21 | Private fork. The miners built blocks on n0's stale local tip, which the rest of TN10 never saw. Those blocks would be discarded once n0 synced. |
| 22:10 | TN10 watch flagged it. |
| 22:21 | TN10 ops stopped the miners and restarted n0 without `--enable-unsynced-mining` (now with `--utxoindex`). |

## Impact

None on the public TN10 network. The forked blocks were only on our node and are dropped on sync. No real testnet rewards came from that window.

## Fix now in place

The miners restart only when all three hold on n0:
- `isSynced` is true,
- `virtualDaaScore` is above 500,000,000 (the real TN10 height, not a fresh node),
- the sink (the node's current tip) is less than 120 s old.

## Lessons

1. Never keep kaspad data in `/tmp`. A reboot wipes it.
2. Never mine on a fresh or unsynced node.
3. `--enable-unsynced-mining` does what it says; it is not a bug. It is only for bootstrapping a brand-new network, never for joining an existing one like TN10.
4. Gate miner start on `isSynced` plus a fresh sink, not on "the process is up".
